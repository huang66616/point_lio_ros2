# Point-LIO / MID-360 优化技术说明

## 目标与版本边界

本轮优化希望降低 Point-LIO 在 MID-360 点云回放中的单帧处理耗时，并尽量保持最近邻结果、地图更新与对外输出行为。优化前基准是 Git 提交 `571696bfcf28b8531ef5a2d2ea153f59124f9b08`；优化后是开发仓库 `optimize/mid360-baseline` 的未提交工作树。短包对照中，真正参与编译的优化差异仅涉及 `include/ikd-Tree/ikd_Tree.cpp`、`include/ikd-Tree/ikd_Tree.h` 和 `src/laserMapping.cpp`。`launch/mapping_mid360.launch.py` 的工作树差异只是将 `runtime_pos_log_enable` 从 `False` 改成 `True`；对照实验对两版使用了相同的 `True` 设置，不能把这项开关算作提速来源。

MID-360 的 `sensor_msgs/msg/PointCloud2` 预处理、`/livox/lidar` 和 `/livox/imu` 话题、`config/mid360.yaml` 与对应 launch 已在上述基准提交中。这些是测试成立的适配基础，**不是本次性能优化新增功能**。候选版另加的运行日志隔离也不属于算法优化。

## 代码改动

| 位置 | 优化前 | 当前实现 | 预期作用与边界 |
|---|---|---|---|
| [`KD_TREE::Nearest_Search`](../include/ikd-Tree/ikd_Tree.cpp) | 构造容量 `2*k_nearest` 的堆；用临时空向量与输出向量交换以释放旧存储；逐个在 `begin()` 插入结果 | 堆容量为 `k_nearest`；输出向量 `clear()` 后按需 `reserve()`；先 `push_back()` 再整体 `reverse()` | 避免反复释放和重新申请输出缓冲，减少头部插入造成的元素移动。`reserve()` 仍可能在容量不足时分配 |
| [`MANUAL_HEAP`](../include/ikd-Tree/ikd_Tree.h) | 每次构造都 `new[]`，析构时 `delete[]` | 容量不超过 5 时使用对象内 `inline_heap[5]`；更大容量仍 `new[]`；按 `owns_heap` 决定是否释放，并禁止浅拷贝 | 常用 `k=5` 的查询不再需要为候选堆单独分配和释放堆内存；不是“所有搜索都零分配” |
| [`KD_TREE::Add_Points`](../include/ikd-Tree/ikd_Tree.cpp) | 每个降采样搜索前用空向量交换 `Downsample_Storage` | 使用 `Downsample_Storage.clear()` | 清空元素并保留容量，可能减少后续范围搜索的重新分配；该项未单独计量 |
| [`lasermap_fov_segment`](../src/laserMapping.cpp) | 开头调用 `cub_needrm.shrink_to_fit()` | 开头调用 `cub_needrm.clear()` | 新一轮地图移动只使用本轮加入的待删除区域，并复用容量；同时改变了旧实现保留元素的行为，需单独验证 |

### 最近邻候选堆与结果顺序

[`Search`](../include/ikd-Tree/ikd_Tree.cpp) 把候选点的距离放入 `MANUAL_HEAP`。堆顶是**比较器优先级最高**的候选；该比较器通常按距离排序，但在距离差小于 `1e-10` 时改按点的 `x` 坐标比较。因此近似等距时，堆顶不一定是数值距离最大的点。`Search` 在候选数达到 `k` 后用堆顶参与替换判断。这是按现有比较器维护候选的大顶堆；“小堆”在这里仅指容量小。该比较器及其近似等距行为在基准提交中已存在，**不是本次优化引入的变化**。现有 [`Estimator.cpp`](../src/Estimator.cpp) 两处调用使用 `NUM_MATCH_POINTS=5`，该常量定义在 [`common_lib.h`](../include/common_lib.h)，因此当前主要路径命中内置容量 5 的分支。

优化前的堆实际由搜索逻辑限制在至多 `k_nearest` 个元素，虽然分配了 `2*k_nearest` 的空间。当前将容量收至 `k_nearest`，与该搜索流程的候选上限一致。弹堆时按比较器优先级依次取出候选：旧代码逐次插入向量头部，当前代码追加到尾部后分别反转点和距离向量，从而保留旧实现对**同一弹出序列**的输出顺序及点、距离的下标对应关系。由于近似等距时比较器按 `x` 坐标决定优先级，反转后的输出**不保证严格按数值距离递增**。比较规则未改；现有端到端记录也不能替代针对近似等距点和其他边界输入的测试。

内置存储使常用 `k=5` 查询省去一次候选堆的 `new[]/delete[]` 配对；输出点向量、距离向量及降采样缓冲只在现有容量足够时避免重新分配。没有独立记录每帧或每次查询的实际分配次数，因此“分配次数减少”是由实现可推断的方向，**不是本报告单独测得的计数**。

### 局部地图待删除区域

`cub_needrm` 是跨函数调用保存的 `std::vector<BoxPointType>`。旧的 `shrink_to_fit()` 只请求缩小容量，**不清空元素**，而且标准不保证一定释放容量。随后代码可能追加本轮的待删除盒并调用 `Delete_Point_Boxes`。当前 `clear()` 会把元素数置零，但通常保留已分配容量，供下一轮 `emplace_back()` 复用；因此它还避免把前一轮元素直接带入下一轮删除请求。这既是潜在的内存复用改动，也是**行为变化**，不能只描述成“释放更快”。现有报告没有逐项消融，也没有记录该分支每次执行的盒数量或单项耗时；不能证明它单独贡献了多少性能收益，更不能据此声称已修复某个实测地图错误。保留容量也不保证 RSS 会下降。

## MID-360 适配与候选版日志管理

基准提交已包含 [`mid360_handler`](../src/preprocess.cpp) 和 [`livox_ros2_pcl::Point`](../src/preprocess.h)，从 PointCloud2 中读取 `x/y/z/intensity/tag/line/timestamp` 等字段。[`mid360.yaml`](../config/mid360.yaml) 配置话题为 `/livox/lidar`、`/livox/imu`，`lidar_type=1`、`scan_line=4`、`timestamp_unit=3`（纳秒）。这些配置适用于已测试的 bag；其他 MID-360 数据流仍需核对字段与标定。

发布候选版在 [`laserMapping.cpp`](../src/laserMapping.cpp) 另外加入**运行文件隔离**：节点启动时用 `mkdtemp()` 在 `POINTLIO_RUN_ROOT` 指定的已存在父目录下创建独立 `pointlio-XXXXXX` 目录；未设置变量时父目录为 `/tmp`。`pos_log.txt`、`mat_out.txt`、`imu_pbp.txt` 及启用 PCD 保存时的点云写入该目录。创建目录、创建 PCD 子目录或打开日志失败时节点返回错误，不回退到源码树 `Log/`。候选版短包验证中，原开发仓库三个 `Log` 文件运行前后 SHA-256 均未改变，见 [VALIDATION.md](VALIDATION.md)。这项改动解决发布和运行时的文件覆盖风险，**没有纳入历史短包优化前后性能归因**。

## 性能证据与测量口径

原始短包证据位于开发仓库 `tools/rosbag_completion_ws/results/comparison_20261031_878e54be42544abcb7119b13fd004903/report.md`，候选版摘要见 [TEST_RESULTS.md](TEST_RESULTS.md)。实验在同一台 i9-12900KS、ROS 2 Humble、Release、同一 `mid360.yaml`、1.0 倍速、关闭 RViz 的条件下，按 pre₁、post₁、pre₂、post₂ 运行；每版本两次。两版加入相同的可开关诊断，并使用相同的外部订阅者。短包时间戳跨度约 36.06 秒，每次播放器自然结束；节点各接收 3607 条 IMU、180 帧点云，176 帧完成常规处理，外部里程计、Path 和注册点云各观察到 176 条。

下表的 P95 先在**每次运行内分别计算**，再对同一版本两次运行得到的 P95 **取算术平均**；并非把两次运行的所有帧合并后重新计算 P95。

| 指标 | 优化前 | 当前工作树 | 解释 |
|---|---:|---:|---|
| 内部单帧耗时均值 | 10.931 ms | 10.397 ms | 减少约 0.534 ms/帧，约 4.88% |
| 内部单帧耗时 P95 | 14.564 ms | 13.932 ms | 两次运行各自 P95 的算术平均；机器汇总值为 14.5635 ms，三位小数显示为 14.564 ms，原报告表显示 14.563 ms |
| 点云回调→外部注册点云订阅均值 | 16.851 ms | 16.350 ms | 减少约 0.501 ms/帧，约 2.97% |

内部耗时 `t5−t0` 从 IMU 处理前计到地图插入后，覆盖 IMU 处理、状态估计/配准和地图插入；**不含**点云回调预处理、等待同步及后续发布。外部指标用同机单调时钟和输出时间戳配对，计到独立订阅者收到注册点云；它还包含发布、DDS 传输和订阅者调度，**不含**bag 发布到节点回调的时间。播放器 publish API 成功不能单独证明 DDS 送达。两次短包对照的 `pos_log.txt` 和 `mat_out.txt` 在记录精度下哈希相同，但不能证明全部内部浮点值逐位相同。

这组数据支持**组合改动在本机、此短包和此配置下的小幅收益**。CPU 采样均值仅略降，RSS 峰值无实质变化；没有每项优化的独立消融数据。候选版后加的日志隔离经过独立构建及短包功能验证，但上述性能数字来自加入日志隔离**之前**的隔离实验副本，不能直接当作候选版的新性能基线。

## 长包结果与局限

开发仓库的 `tools/rosbag_completion_ws/results/long_optimized_retry_20261031_5fdb722e26c541149cdf7cd2eed45fc2/report.md` 记录了一次**优化版**约 277 秒长包测试：节点接收 55,435 条 IMU、2772 帧点云，其中 2768 帧完成常规处理；退出前点云内部队列为零。播放器自然结束，节点在等待期后由脚本主动 SIGINT 停止。该长包**没有同条件优化前版本对照**，因此不能声称长包性能已经提升。

该次长包后半段内部耗时、外部订阅延迟和 RSS 均上升。地图规模、点数、Path 消息大小及观察者调度等因素尚未逐项隔离；现有证据既不能把趋势归因于上述优化，也不能判定为内存泄漏。后续若要归因，应在独立副本中固定同一 bag 与参数，分别做最近邻缓冲、堆内置存储、降采样缓冲和地图容器改动的消融，并记录每项的调用次数、分配次数、地图规模及输出一致性。不要把短包内部耗时与不同数据内容的长包数值直接相减作为提速证据。
